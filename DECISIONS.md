# DECISIONS.md

One line per decision taken where SPEC.md left room for interpretation.

- Meta route `memberCount` returns the live count when the room runtime is loaded, otherwise `0` (members are not persisted).
- Unknown REST routes answer `404 { "error": "INVALID_INPUT" }` since `ErrorCode` has no generic NOT_FOUND entry.
- New members start with status `focusing` (first entry of `STATUSES`).
- `timer:reset` acks and broadcasts even when the timer was already in the reset state (keeps clients convergent).
- REST body parse failures (malformed JSON / too large) map to `400 INVALID_INPUT` instead of `500`.
- Prisma message pruning uses an in-process counter (spec allows it; single-instance server).
- The password failure limiter is a sliding-window counter (5 failures/min per IP+room) rather than a token bucket, matching "5 failures per minute" semantics exactly.
- `room:join` re-join with the same clientId refreshes the nickname (sanitized + de-duplicated) but keeps the original `joinedAt`.
- Boot recovery applies `complete()` at most once per room, as specified; with `autoStart` the next phase is then scheduled normally.
- "Host menu" is a three-dot popover on each member row (`MemberMenu`): timer control, make host, mute, kick, ban. Role changes and removals ask for confirmation first; mute is a one-click toggle the host can reverse just as fast.
- Chat system lines are stored as translation keys + params and translated at render, so switching language retranslates the visible history.
- Phases 6 and 7 were implemented together: the timer card and the room page are one screen and share the same connection hook.
- `MAX_MEMBERS` is validated with `.max(30)`, so the SPEC cap cannot be raised through the environment.
- Root `postinstall` runs `prisma generate`; npm's allowScripts policy skips Prisma's own postinstall, and without the generated client `npm run typecheck` fails on a clean clone.
- `dev:memory` passes `--memory` as an argv flag (read in `config.ts`) instead of using `cross-env`, which SPEC excludes.
- Typing indicators expire locally after 3 s, so a lost `chat:typing false` cannot leave a stuck indicator.
- Client acks time out after 10 s and report `INTERNAL`, so a dropped ack cannot leave the UI waiting forever.
- `roomStore.timerState` ignores an event whose `version` is older than the current one (out-of-order guard).
- The Docker runtime image keeps devDependencies because the SPEC-mandated CMD runs `npx prisma db push`, and SPEC pins the Prisma CLI as a dev dependency.
- The Docker image build was not run locally (Docker daemon not started); `docker compose config` validates `docker-compose.yml`.
- Browser-driven acceptance (two tabs, themes, chime, refresh mid-run) could not be automated in this environment and is listed as manual verification steps.

## Added after the SPEC build (2026-11-08, requested by the owner)

- **Moderator role.** `Member.isModerator` is a second, lower tier: the host stays single (settings, roles, host transfer) while a moderator only gains timer control (`start`/`pause`/`reset`/`skip`). Chosen over multiple hosts so that "who owns the room" stays unambiguous.
- The flag is presence state, held in memory like `status`/`task`: it is not persisted, and it is dropped when the member leaves or the server restarts.
- Becoming host — by transfer or by auto-transfer — clears `isModerator`, so a member never holds both roles.
- Appointing a moderator is host-only (`member:setModerator`, Zod-strict payload) and cannot target the host or an unknown/offline user.
- `settings.timerControl: 'host'` now means "host and moderators". The enum values are unchanged so stored rooms and the shared schema stay compatible; only the label changed to "Host & moderators".
- Chat name colours: host gold (`text-yellow`), moderator silver (`text-subtext1`), everyone else mauve. The colour is resolved from the live member list, so a message from someone who already left falls back to mauve. Own messages keep no name line, per SPEC 8.2.
- Copy link falls back to a hidden `<textarea>` + `document.execCommand('copy')` when `navigator.clipboard` is missing or rejects — which is what happens in an embedded browser over plain http. Failure now toasts `toasts.copyFailed` instead of the misleading `errors.INTERNAL`.

## Member moderation (2026-11-08, requested by the owner)

- The two hover icon buttons on a member row became one three-dot popover (`MemberMenu.tsx`) holding timer control, make host, mute, kick and ban. It is positioned `fixed` against the trigger, because the members list scrolls and would clip an absolutely positioned menu; it closes on Escape, outside mousedown, scroll or resize.
- Role changes and removals go through `ConfirmDialog` first — the owner asked for a confirmation on role changes, and a kick/ban cannot be undone from the row either. Mute/unmute applies immediately since one more click reverses it.
- **Mute.** `Member.isMuted` is presence state like `isModerator`: host-only toggle, checked in `sendChat` (ack `MUTED`) and in `setTyping` (dropped silently, so no indicator is broadcast). It is not persisted, so a member who drops past the grace window comes back un-muted.
- **Kick and ban share one mechanism**: a `RoomBlock` row keyed by `(roomId, userId)` with a nullable `expiresAt`. A kick writes `now + KICK_COOLDOWN_MS` (15 min) and lapses on its own; a ban writes null and lasts until the host lifts it. Only the public `userId` is stored — `clientId` is a secret per SPEC 9.
- The block is checked at the top of `room:join`, before the password and capacity checks, so a removed person cannot get back in under a new nickname. Expired kicks are pruned lazily when that id is next looked at, so the store needs no timer of its own.
- A host-ordered removal emits `room:kicked {userId, reason}` instead of `member:left`. That is what lets the removed person's own tab clear its stored session and show the "you were removed" screen rather than auto-rejoining in a loop.
- Neither the host nor an unknown/offline id is a legal target (`INVALID_INPUT`), and only the host may moderate (`FORBIDDEN`), so a guest can never kick the host to take the room — auto-transfer already covers the host leaving.
- **Blocked list.** `room:getBlocks` (host-only) returns who is kept out with the nickname they had at removal time, so the list is readable; `member:unban` lifts a block early and the row disappears.

## UI readjustments (2026-11-09, requested by the owner)

- **Invisible card titles.** `--color-base` is a theme colour, so under Tailwind v4 `text-base` resolves to *colour* `base` (the page background), never the 1 rem font size — `Home.tsx` was painting "Create a room"/"Join a room" in the background colour. Card titles now use `text-[1rem] text-text`. Where the colour really is wanted (`Button`, the chat send icon) `text-base` stays. Note `text-text` and `text-sm` are unaffected: only `base` collides with a size name.
- Placeholder text moved from `overlay0` to `subtext0` in every input (2.1:1 → 4.1:1 on Latte, 3.6:1 → 7.9:1 on Mocha).
- **Two theme modes, system default.** `ThemePref` keeps `'system'`, but only as the "never chosen yet" value: the inline script and `resolveFlavor` still follow `prefers-color-scheme`, and the first click pins the choice to `light`/`dark`. `setTheme` now takes `Exclude<ThemePref, 'system'>`, so nothing can put it back programmatically; `cycleTheme` and the `theme.system` label are gone, and the toggle shows the flavour you are *looking at*, not the stored pref.
- **Font.** The whole UI is JetBrains Mono at the owner's request. `--app-font` lists `JetBrainsMono Nerd Font` (and `… Nerd Font Mono`) first so a locally installed patched variant — with its icon glyphs — beats the bundled `@fontsource-variable/jetbrains-mono` webfont, which in turn covers visitors who have nothing installed. Both `--font-sans` and `--font-mono` point at `--app-font`, and `body` uses that variable directly instead of `--font-sans`, since `@theme inline` is free to drop a theme variable nothing else references.

## Timer sound presets (2026-11-09, requested by the owner)

- The phase-change chime was one hard-coded two-note sine motif; it is now 10 synthesised voices (`client/src/lib/soundPresets.ts`) selectable from a dialog in both headers. Everything stays WebAudio-only: no audio assets, no storage, no bandwidth, and the server does not learn about it.
- Each preset is data (`wave` + `{freq, at, dur, gain?, glideTo?}`), so the module is pure and unit-testable, and `sound.ts` keeps a single scheduling loop. Notes are capped at gain 0.2 and square/sawtooth voices are written quieter than sine ones, since equal-gain oscillators sum and clip.
- One motif serves both phase changes: `reversePreset` mirrors the note onsets, so entering focus plays the preset as written and leaving it plays it backwards. That keeps the old rising/falling distinction for all 10 voices instead of authoring 20 note lists.
- The choice is a device preference in `prefsStore` (`soundPreset`, default `classic`) rather than room state or a `RoomSettings` field — nobody else hears it, so it needs no schema change, no migration and no broadcast. `findPreset` falls back to `classic`, so a value written by a future build cannot silence the chime.

## SPEC-ADDON Phase 10 — foundations (2026-11-09)

- **Feature A already existed, so nothing was re-built.** Moderators are the pre-existing `MemberEntry.isModerator` flag and `member:setModerator` event; the spec's `room:setMod {isMod}` was *not* added under a second name. The three gaps rule 9(a) asked for are closed: `Member.role` (`host`/`mod`/`member`) is derived server-side in `toMember` and re-derived by the client on `room:hostChanged`; promotions are persisted in a new `Room.modClientIds String[]` and replayed into `isModerator` when that clientId joins, so the tier now survives a reconnect *and* a restart; and a single `canControl(clientId)` helper (host or mod) now backs `canControlTimer`, which every `media:*` handler will reuse in Phase 15. Host transfer, manual or automatic, deletes the new host from `modClientIds` in the same write as the host change.
- `RoomSettings.strictFocus` and the media columns are additive with defaults (`false`, `null`, `false`), mapped in `schema.prisma`, `prismaStore` *and* `memoryStore`. Nothing needs `db:push`-free migration: existing rows take the defaults.
- **`mediaMachine` is namespaced on the shared barrel** (`export * as mediaMachine`). Its `play`/`pause`/`clear` collide with the timer machine's exports, and renaming either set would break the established `start as startTimer` import style in `RoomRuntime`. Callers write `mediaMachine.pause(state, now)`.
- `createInitialMedia(now)` takes the clock where the spec's sketch took nothing: `anchorAt` is a server timestamp, and `0` would make `positionAt` report a huge position for the whole epoch. Same reason `RoomRuntime` builds its reload state from that helper plus the stored `videoId`/`loop`.
- The playhead is deliberately not persisted (spec 3.1): a room reloaded from the store comes back `{ status: 'paused', anchorPositionMs: 0 }`, i.e. the video is still there but nobody gets audio without a controller pressing play.
- `Member.focus` ships as part of the type contract now, filled with the neutral "not tracking" value, because `RoomSnapshot` and `member:updated` are already typed as a whole `Member`. `focusTracker` replaces that literal in Phase 14; no client can render a half-shaped focus object in the meantime.
- The seek cap became `MAX_SEEK_MS = 86_400_000` in `constants.ts` instead of a magic number inside the Zod schema, so the schema test can assert both bounds.
- **Local prefs grew all at once** (spec 4.1) in a new pure module, `client/src/lib/prefs.ts`: value types, `PREF_DEFAULTS`, `PREFS_STORAGE_VERSION` and `migratePrefs`. Keeping it store-free means the migration is unit-testable in plain node — there is no jsdom in this workspace — and `prefsStore` stays a thin zustand wrapper over it. `migratePrefs` fills missing keys with defaults, ignores values whose type does not match, and drops keys that no longer exist, so a hand-edited localStorage entry cannot poison a slider.
- `soundPreset` (the ten synthesised voices) is *not* renamed to `alertSound` in this phase: `SoundPicker` still uses it. Phase 12 introduces `alertSounds.ts` with the spec's five-sound table, moves the call site, and maps the old value over in a migration. Both keys coexist for exactly those two phases.
- `client/src/lib/audio.ts` now owns the single lazily created `AudioContext`, the first-gesture resume listeners, and one `GainNode` bus per feature (`alerts`, `ambient`). `sound.ts` lost its module-level context and schedules onto the `alerts` bus, which is what lets the ambient engine (Phase 13) and the alert volume slider (Phase 12) set their own levels without touching each other.

## SPEC-ADDON Phase 11 — preset gaps + timer display style (2026-11-09)

- **Rule 9(b) checked against the code: there was no Pomodoro preset UI to merge.** The only presets in the repo are the ten synthesised *sound* voices (`lib/soundPresets.ts`, `SoundPicker`) — a different feature with its own `sound.presets.*` namespace, so those names stay untouched. The four `TIMER_PRESETS` rows are the first timer presets; `SettingsDialog` grew a chip row above the number inputs instead of a second dialog, so nothing is duplicated.
- Preset matching lives in pure `client/src/lib/timerPresets.ts` (`matchPreset(values) → id | 'custom'`) because this workspace has no jsdom: a component test would need one, a function test does not. `PresetValues` deliberately types only the four numbers a preset owns, so `autoStart`/`timerControl` can never make a room "custom".
- Clicking a chip edits the draft only; applying stays the existing Save → `room:updateSettings` path. One write, one permission check, one broadcast (`room:settingsUpdated`) — which is what updates every other client's inputs and summary line.
- The "Custom" chip is a `<span>`, not a button: clicking it would be a no-op, and an inert control reads as a bug. It appears only when no preset matches, styled like a selected chip.
- Two label dictionaries rather than one. `settings.presets.*` carry the ratio ("Deep Focus 50/10") because the chip is where you pick a shape before touching the inputs; `timer.preset.*` hold the bare name ("Deep Focus") because the summary line already prints the numbers and would otherwise read "Deep Focus 50/10 · 50 / 10 / 30 min". `timer.summary` gained a `{name}` placeholder in both languages.
- The summary line now renders for the host too (spec 4.3: *everyone* sees the preset name). It used to be non-host-only.
- `timerStyle` is a device pref (`ring` default), never room state: the ring or the bar is presentation, and two people in one room are allowed to disagree.
- `TimerBar` is the minimal display — large digits, phase label, a thin linear bar in the same phase colours as `TimerRing`, and the cycle dots, so nothing is lost when the ring goes.
- `SoundDisplayPopover` is a new header entry point built on the `MemberMenu` popover recipe (fixed against the trigger, closes on Escape / outside mousedown / scroll / resize). Under 640 px it becomes a bottom sheet, since an anchored 232 px panel on a 360 px phone is an island.
- The Alerts and Ambient groups are not in that popover yet — Phase 12 (alert table + preview) and Phase 13 (ambient engine) own those controls. The Display group on its own is complete and usable today.

## SPEC-ADDON Phase 12 — alert sounds (2026-11-09)

- **The ten-voice chime picker is replaced, not extended.** Spec 4.1 fixes `alertSound` to exactly five ids, and rule "no duplicated preset UI" rules out a second sound dialog, so `lib/soundPresets.ts`, `lib/sound.ts` and `components/SoundPicker.tsx` were deleted (owner-approved) and `lib/alertSounds.ts` — the spec's note table plus its scheduler — is now the only alert engine. The voices with no counterpart in the table (`beep`, `gong`, `pluck`, `arpeggio`, `sweep`, and the original `classic`) are gone from the picker.
- That loss is softened rather than ignored: `migratePrefs` maps each stored `soundPreset` onto the closest surviving sound (`gong → bell`, `arpeggio → chime`, `beep`/`pulse → pulse`, `pluck → marimba`, `sweep → pulse`, `classic → chime`), so nobody's choice resets to the default. `PREFS_STORAGE_VERSION` is now 2, which is what triggers that one-time mapping; an explicit stored `alertSound` always wins over the legacy key, and an unrecognisable legacy name falls back to the default instead of throwing.
- `alertSounds.ts` is data + scheduling only, so the table is unit-testable without WebAudio: five ids exactly, positive frequencies, non-negative and ascending note onsets, durations ≤ 2 s, relative gains in (0, 1], both variants present and *different* for every sound that makes noise, and `master × sound gain × loudest note ≤ 1` so nothing can clip at volume 100. `none` carries `wave: null` and empty variants, and `playAlert` returns before touching `getAudioContext()`, so the silent option never opens a context.
- Level follows the spec literally: `volume/100 × 0.5 × sound.gain × note.g`, 10 ms attack, exponential decay to 0.0001 at the note end, on the shared `alerts` bus from Phase 10. `pulse` is written at ×0.3 because a square wave sums and clips.
- **Preview is per sound, as a small play button on each row**, not one button for the selected row — that is what "a Preview button per sound" asks for and it lets you audition a sound before committing to it. Choosing a radio also previews it, which is how the old picker worked, and the hint line says so.
- Preview schedules both variants 600 ms apart measured **from each variant's start**, per the spec's "600 ms apart"; on the bell (0.9 s decay) the two therefore overlap slightly rather than leaving a gap.
- The Alerts group lives in the Phase 11 `SoundDisplayPopover` alongside Display, and it owns the master mute switch (`soundOn`) the spec lists for that group. The header keeps the one-click `SoundToggle` speaker icon, so the pref is now editable in two places: the switch for people who want to see what they are toggling, the icon for a fast mute.
- `Home` swapped its `SoundPicker` entry point for the same popover, so the sound can still be chosen before joining a room. On the room page the header went from four icon buttons to three.

## SPEC-ADDON Phase 13 — ambient sound (2026-11-09)

- Generation and looping are pure (`client/src/lib/noise.ts`), wiring is not (`lib/ambient.ts`). That split exists because this workspace has no jsdom: every property the spec lists for the generators — lengths, values inside [-1,1] after `normalize`, determinism from a seeded rng, |mean| < 0.05, brown smoother than white — is asserted on plain arrays, and the seam crossfade is asserted with hand-computed numbers.
- `loopBuffer(samples, fade)` folds the tail over the head instead of trusting a zero-value boundary: pass `length + fade` samples, get `length` back, with the first `fade` samples being a linear blend of head and tail. Real noise does not end at zero, so a plain loop point is an audible click.
- The mean test uses a 262 144-sample run (`MEAN_LENGTH`), not the 4096 used by the other properties. Kellet's pink filter is a set of decaying accumulators: over a few thousand samples it still carries its own start-up offset (measured ±0.08 with the test's seed), which the spec's 0.05 bound is not meant to describe. Brown is left out of the assertion for the opposite reason — a random walk genuinely wanders, and the lowpass/gain stage in `ambient.ts` is what keeps it usable.
- `type Samples = Float32Array<ArrayBuffer>` is exported from `noise.ts`. Since TS 5.7 the typed-array generics are literal, and `AudioBuffer.copyToChannel` only accepts an `ArrayBuffer`-backed array; without the alias every generator signature would need a cast at the call site.
- Buffers are 6 s, stereo, with an independent rng run per channel — the same noise written to both sides would be mono with extra steps — and they are cached per `${type}@${sampleRate}`, so returning to a colour costs no CPU and cannot re-trigger a start transient.
- `startAmbient(type, volume)` is also the volume setter: if the requested type is already playing it delegates to `setAmbientVolume` and returns. Rebuilding the source to move a slider would click and reset the loop phase, and it lets `useAmbient` get away with one effect instead of two.
- The autoplay gate needed no new machinery. `lib/audio.ts` (Phase 10) already installs first-gesture `click`/`keydown` resume listeners on the shared context, and `startAmbient` calls `resumeAudio()` again for the case where a suspended context is handed a pref that says "play". A pick from the popover *is* the gesture.
- Names are `startAmbient` / `stopAmbient` / `setAmbientVolume` rather than the spec's `start` / `stop` / `setVolume`, which would import as three unqualified module-level verbs.
- Ambient is strictly local: no socket event, no server field, no room state. The only thing another person can infer is that *you* have a voice running, from the mauve tint on the header trigger.
- `ambientOnlyWhileFocus` reads `timer.status === 'running' && timer.phase === 'focus'` from `roomStore`, so the fade follows the server-authoritative timer — including a host starting or stopping the room — without any dedicated plumbing. Volume changes keep the running voice; only the ramp moves.
- rain and waves use an oscillator → depth-gain → `gain.gain` pair, with the base level multiplied by the voice's `offset` (rain 1.0 ±0.08, waves 0.5 ±0.5), so the swell never has to be faked by re-scheduling levels from JS.
- `useAmbient` is mounted on `RoomPage` **and** `Home`, because both pages host the popover; a control with nowhere to route would read as broken. Its unmount effect calls `stopAmbient()`, which is spec 4.5's "stops on leaving the room page".

## SPEC-ADDON Phase 14 — focus tracking (2026-11-09)

- The accounting lives in `server/src/focus/focusTracker.ts` as pure state transitions on a single `FocusTrackerState` object, so the whole spec ("only a running focus phase counts", "a pause freezes but never ends", "an away interval that spans a phase boundary is counted once") is testable without a socket, a room or a clock. `RoomRuntime` only decides *when* to call it and what to emit.
- "Active window" is one boolean the server already knows: `roomActive = timer.status === 'running' && timer.phase === 'focus'`. The client never sends a duration, never sends a timestamp and never sends anything about a tab or an app — `focus:state` carries exactly `{away: boolean}`, and `awaySince`, `awayCount` and `awayMs` on `MemberFocus` are measured by the server from its own clock. That is the whole privacy surface, and it is why no new DB column was needed beyond the Phase 10 `strictFocus` setting.
- `setTracking` / `setAway` / `onRoomActiveChange` return the *same object reference* when nothing changed, which is how `RoomRuntime` decides whether an `member:updated` broadcast is warranted. Events therefore fire on transitions (opt-in, away start/end, phase start/end), never on a tick — a room of 30 tracked members stays silent while everyone is present.
- The tradeoff inside that rule: `awaySince` is part of the projection, so the moment a phase ends mid-away the member gets one more update that closes the live counter in the UI. Without it the away chip would keep counting up through the break, which is a lie.
- Every timer write goes through `syncFocus(before, reason)` — `timerAction`, `updateSettings` and `onPhaseEnd` — rather than each path remembering to do it. Settings are included because changing `focusMin` can stop a running focus phase; it can end a *phase* but never a *session*, which is what `focusEndReason()` encodes: only `complete`, `skip` and `reset` close one.
- `resetSession` runs for untracked members too. Opting out deliberately leaves the counters alone until the session ends (so the chip does not vanish mid-break), and that stored time must not leak into the next session.
- A `focus:summary` event is emitted only when at least one tracked member measured `activeMs > 0`. A room where nobody opted in gets nothing, so no dialog appears to explain that there is nothing to report.
- `focus:state` is limited to 10 reports per 10 s per socket and **silently dropped** past that, per spec 9 — an error here would be a client bug the user can neither see nor fix, and the away flag is not something to argue about. `setFocusAway` from a member who never opted in is `FORBIDDEN`, because honouring it would let a client start a timer it did not agree to.
- `useFocusTracking` listens to `document.visibilityState` only. Window blur/focus was rejected: the Phase 15 YouTube iframe and any DevTools or dialog interaction trip it, and the spec measures the tab, not the window. The 3 s debounce is client-side (`FOCUS.AWAY_DEBOUNCE_MS`) and re-checked when it fires, so a fast alt-tab never reports anything at all.
- Opt-in is re-sent on every connect rather than trusted to the stored pref, and the hidden-at-that-moment case is replayed immediately — otherwise a reload while the tab is in the background would show "present" forever.
- Opting out announces `setFocusTracking(false)` to the room only if the user is still in a connected room. Leaving the room also flips `focusTracking` to false in the store, and announcing that would fire a `FORBIDDEN` toast on the way out for no reason.
- Consent is asked once per room code (`session.ts` keeps the list) and only when the room has `strictFocus` on, because that is the case where the absence of tracking is visible to others. Declining is remembered locally, not by the server.
- The `focusTracking` pref got a visible switch in `SoundDisplayPopover` (a fourth group, beyond the three that spec 4.7 lists). Without it, a person who declined the consent dialog would have no way to change their mind short of clearing storage — an invisible control reads as a bug.
- `sortSummaries` lives in `lib/focusHistory.ts`, not in the dialog that uses it. Client tests can only import DOM-free modules, and ranking ("best focus first, then fewest away intervals, then name") is exactly the kind of rule worth pinning down.
- `formatSpent` was added next to `formatRemaining` rather than folding the two together: the spec asks for `1m 20s` in the away chip and `m:ss` in the summary columns, and one formatter with a flag would have made both call sites harder to read.
- The away chip shows a live `· 0:07` tail only while `awaySince` is set, and `AwayClock`/`OwnFocusLine` are separate components so the 1 s `useNow` tick is scoped to the rows that display it instead of re-rendering the member list.
- History is 10 entries in localStorage (`studyroom.focusHistory`), 5 shown, parsed defensively: `parseHistory` re-clamps and drops anything that is not shaped like an entry, because that file is user-editable and the dialog would otherwise render `NaN%`.
